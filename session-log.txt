### Immutable fixture and baseline design
A fixture is a self-contained, approved, immutable evidence package. It freezes both the exact input and the Azure output that Cloudflare must compare against; comparison never reruns Azure.

```text
fixtures/{fixture-id}/{manifest-sha256}/manifest.json
fixtures/{fixture-id}/{manifest-sha256}/input/transcript.vtt
fixtures/{fixture-id}/{manifest-sha256}/baseline/azure-normalized-output.json
fixtures/{fixture-id}/{manifest-sha256}/baseline/azure-publication-intent.json
fixtures/{fixture-id}/{manifest-sha256}/baseline/config-snapshot.json

runs/{run-id}/model-response-checkpoints/normalized-output-v2.json
runs/{run-id}/cloudflare-normalized-output.json
runs/{run-id}/cloudflare-publication-intent.json
runs/{run-id}/comparison.json
runs/{run-id}/comparison.md
```

The manifest binds fixture ID/revision, acquisition mode, source identity, every object SHA-256, Azure pipeline/prompt/model/deployment identity, configuration hashes, classification, approver, timestamps, and expiry. Any changed transcript, baseline, configuration snapshot, processing contract, or manifest is a new revision requiring approval. Fixture and run data are intended to expire after 30 days.

The Azure baseline comprises a complete `NormalizedOutput` plus a separate `PublicationIntent`. The Worker verifies that the separate intent equals the intent embedded in Azure normalized output before comparison. This prevents a technically valid result from silently changing what would be published.

Cloudflare must reproduce immutable source and processing fields from the manifest. Comparator severity is:
- **Blocking:** source/hash/schema/processing-contract drift, assertion drift, validation drift, or publication-intent drift.
- **Material:** topic count/classification, ownership/confidence, people attribution, or meeting classification drift.
- **Permitted:** explicitly approved non-semantic formatting or ordering variation only.

### Checkpoint and retry design
The Worker persists model output before final artifacts and D1 completion. On downstream failure, recovery keeps the same run ID and reuses a checkpoint only when its output-contract version, response hash, normalized schema, transcript hash, and fixture processing contract all validate. The older schema-invalid checkpoint remains immutable audit evidence. `normalized-output-v2` writes a separate versioned checkpoint rather than overwriting it.

### Verified request-to-artifact path
1. `POST /v1/fixture-runs` authenticates with the submission token and safely reserves or recovers a D1 run.
2. The Queue consumer claims only the queued reservation and validates the manifest plus all R2 hashes.
3. The Worker invokes Azure OpenAI through the direct API-key Chat Completions contract and requires exactly one JSON `NormalizedOutput`.
4. It checkpoints, validates, compares against the frozen Azure baseline, and writes Cloudflare output plus JSON/Markdown comparison artifacts.
5. A run becomes `completed` even when comparison is `blocked`; blocked is a valid parity finding rather than a processing crash.
