### Key design notes

| Pattern | How it works |
|---------|-------------|
| **Hard FK** | `topic_occurrences.topic_id → topics.topic_id` and `topic_merge_candidates.topic_id_a/b → topics.topic_id` — enforced by SQLite |
| **Soft links** | Everything else using `meeting_ref` — no FK, just a consistent string value shared across tables. Allows transcripts to be registered independently of participants/occurrences |
| **JSON columns** | `decisions`, `actions`, `risks`, `retrieval_anchors`, `follow_up_flags`, `stance`, `topics_referenced` — stored as JSON strings. The standalone `actions/decisions/risks` tables are the normalised form for querying; the JSON in `topic_occurrences` is the source snapshot |
| **R2 pointers** | `r2_key` on transcripts, `r2_key` on topic_occurrences, `contributions_r2_key` on participants, `source_r2_key` on actions/decisions/risks — all point into R2 for the actual file content |
| **Empty tables** | `actions`, `decisions`, `risks` have schema but no data yet — population from people files is next backlog item |
